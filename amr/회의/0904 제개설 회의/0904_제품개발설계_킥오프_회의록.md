## 1. 현재까지 구현된 내용 (안정민 선배 발표)

### 1.1 전체 구조
- Planner → 0.2 s 간격 **20개 waypoint** 전달 (pose `x, y, θ` + 속도 `vx, vy, yaw rate`, 총 6축)
- MPC가 이를 받아 입력 계산 → 모터 드라이버 → 출력
- 매 스텝 time-shift 하며 planner가 갱신 (receding horizon 구성 O)

### 1.2 모델링
- 모터 + 드라이버 내부는 **블랙박스** → 입·출력 비교로 **1차 시스템 + dead time** 피팅하여 액추에이터 전달함수 `G` 식별
  - 실제 의미: "명령 속도 대비 실제 출력 속도"(인코더 기준), 즉 하위 제어루프의 응답 특성
- 메카넘 kinematics(비선형) → **레퍼런스 경로 주위 1차 테일러 선형화**
- 결과: 에러 다이나믹스 상태(위치·속도 오차) → 이산화하여 `A_k`, `B_k` 도출
- **LTV(Linear Time-Varying)** 로 구현: 매 스텝마다 다른 A, B를 누적 곱 → 솔버 연산량의 지배적 요소
- 이전 스텝 속도 명령 `g`를 상태에 포함한 **증강 상태(augmented state)** 구성

### 1.3 비용함수 / 제약 / 솔버
- 출력 스케일이 `m/s` 2개 + `rad/s` 1개라 Q 대각항으로 스케일링
- 가속도 제약, 입력 제약(각속도 기반) 적용. **출력 제약은 연산량만 늘고 효과 미미**
- Np, Nc 등 튜닝 파라미터는 경험적으로 설정
- 표기·구조를 MPC 교재와 동일하게 맞춰 팀원 이해도 확보

### 1.4 기타
- Odometry 좌표계 설치가 관례를 안 따라 위치추정이 발산 → 관례대로 수정 후 정상화
- 현 상태로도 성능은 양호 (팔자 주행 등)

## 2. 교수님 핵심 피드백

### 2.1 지금 것은 "컨트롤러"가 아니라 "플래너"다
- 컨트롤러라면 최종 출력이 **액추에이터에 직접 들어가는 물리 입력**(토크 / 전류 / 각속도)이어야 함
- 현재 MPC 출력은 `vx, vy, yaw rate`의 변화량 → 사실상 **경로 스무딩(상위 제어기 = 플래닝)**
- 구조를 **Upper controller(planning) / Lower controller(kinematics + actuator)** 로 분리해서 볼 것
  - 지금은 lower controller를 전달함수 `G` 하나로 뭉뚱그려 매핑해 둔 상태
- ⇒ **MPC는 가장 아랫단(모터 토크 or 전류)부터 다시 구성**하는 것이 좋음

### 2.2 Odometry 사용 금지
- 슬립이 상시 발생하는 시스템이므로 휠 오도메트리 기반 위치추정은 신뢰 불가
- **Localization(SLAM / Particle Filter)** 으로 차량 위치·속도를 얻는다고 가정 (연구실 자산 활용)
- 로보레이서 경험자가 미경험자(준민 학생)에게 localization 큰 그림 공유할 것

### 2.3 Planner 인터페이스
- 속도항을 **글로벌 / 로봇 좌표계 둘 다** 전달받고 취사선택 (planner 쪽에서 transpose 한 번이면 됨)
- 어느 쪽이 유리한지 비교해 볼 것

### 2.4 재정의할 시스템 다이나믹스 (점질량 + 외란 통합)
```
ẋ_e = v_e
v̇_e = T·I⁻¹·τ  +  d  −  v̇_r
```
- 앞항: 모터 다이나믹스 (`τ = I·ω̇`, `ω → v` 매핑이 `T`이므로 `ω̇ → v̇`도 동일 매핑)
- `d` = **모델링하지 않은 모든 것**을 몰아넣은 disturbance
  - 슬립으로 인해 전달되지 않은 토크
  - kinematics 행렬 `T`의 불완전성 (대각 바퀴만 굴렸을 때 헤딩이 틀어지는 등)
  - **하중 변화에 따른 관성 `I` 변화**
- 메카넘 휠의 롤러 다이나믹스까지는 고려하지 않고, kinematics로 기술 + 나머지 고차항은 전부 disturbance 처리

### 2.5 해결 방향: 2안 채택
| 방향 | 내용 | 판단 |
|---|---|---|
| ① Disturbance Observer / Robust Control로 `d`를 직접 처리 | 직접적인 휠슬립 제어가 아니라 "시스템을 잘 찾아 올바른 제어" | **너무 어려움 → 제외** |
| ② `d=0` 가정으로 MPC를 풀어 **nominal input(토크)** 을 구하고, 여기에 **슬립 억제 보상항**을 더함 | 민철 학생이 진행 중인 슬립 보상 기법과 동일 맥락 | **채택** |

- MPC의 receding horizon 특성(100스텝 예측 중 1스텝만 사용)만으로도 어느 정도 피드백은 되지만 부족 → 보상항 필요

### 2.6 슬립 추정 방법
- **센서로 얻을 수 있는 값**: 4개 바퀴의 각속도 `ω`(모터 인코더) + 토크/전류, 그리고 localization 기반 차량 pose·속도
- 두 가지 방향 중 선택:
  1. **역기구학**: `T⁻¹ · (vx, vy, yawrate)` 로 "슬립이 없다면 나와야 할 휠 각속도" 예측 → 실측 `ω`와 비교 (예: 예측 10 rad/s vs 실측 15 rad/s → 슬립)
  2. **순기구학**: 실측 `ω`에 `T`를 씌워 관측 `vx, vy` 계산 → localization 속도와 비교
- 물리적 해석(슬립 자체)은 ①이 낫고, 성능 관점(차량이 제대로 가는 것)은 ②가 나음 → 팀에서 선택
- **종/횡 구분보다 바퀴 4개 각각에 대해 산정**하는 것을 권장
- 원리: *모든 disturbance = (nominal 모델 예측값) − (실제 관측값)*
- **Observer는 올해 불필요** — 측정값 정확도가 문제될 경우 2차년도에 추가

## 3. 하드웨어 · 과목 운영 관련

- 노유정 교수님 코멘트: SW 중심이어도 **하드웨어 설계 요소가 있어야 성적에 유리**
- AMR을 새로 제작하지는 않고, 대신:
  - **토크(또는 전류) 제어가 가능한 모터로 교체** + 그에 맞는 **모터 드라이버 교체**
    - 현재 모터는 느리고 상태가 좋지 않음 / 드라이버는 현 모터 전용이라 같이 교체 필요
    - 전류 제어까지만 되어도 충분 (토크와 거의 비례)
    - **모터 선정 근거 + 토크제어 가능성**이 곧 하드웨어 설계 산출물
  - **시나리오 환경 구성**(노면 종류 다변화, 중량 부가)도 하드웨어 기여로 인정
- **예산**: 1인당 30만원 × 4명 = 약 120만원 → 모터 구입 가능. 부족분은 연구실에서 지원
- 리드타임이 길 수 있으므로(수개월) **모터 발주는 최대한 빨리**, 대기 기간에는 MPC 스터디
- 시뮬레이션에서 **메카넘 롤러 구현이 잘 안 됨** → 시뮬 매달리기보다 **실차 하드웨어 데모**가 오히려 로드가 낮다고 판단 → **하드웨어 방향으로 결정**
- 연차 구분
  - **1차년도(이번 학기)**: 컨셉 개발 + 소프트웨어 개발, **단일 시나리오**에 대한 실차 시연
  - **2차년도**: 실제 제품 개발, 시나리오 세분화(노면·하중), 관측기 추가 등 성능 개선
  - ⚠️ 이번 학기에 다 보여주면 다음 학기에 할 게 없음 + 로드 과다 주의
- 업체 요구사항을 전부 지킬 필요 없음. **주제는 끝날 때까지 바꿔도 무방**
- 최종 발표: 하드웨어 구성 + 외란/노면 변화에도 경로를 잘 추종한다는 것을 (최소 시뮬레이션에서라도) 시연
